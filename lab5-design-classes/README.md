## 1. Цель и метод

**Цель:** превратить модель предметной области (лаб. 2) и диаграммы коммуникаций (лаб. 4) в модель
проектирования: классы с атрибутами, операциями и зависимостями, по которым в лаб. 6 можно писать код,
не меняя словарь предметной области.

**Метод — BCE + слои.** Классы разделены на пять групп, ровно как в [DESIGN.md §6](../DESIGN.md):

| Слой | Стереотип | Назначение | Сколько |
|---|---|---|---|
| Границы | `<<boundary>>` | по одному экрану на прецедент; знает только управляющий слой | 4 |
| Управление | `<<control>>` | сценарии операций, проверки инвариантов, координация | 4 |
| Сущности | `<<entity>>` | понятия предметной области, только атрибуты | 13 |
| Репозитории | `<<repository>>` | сохранение и поиск агрегатов | 3 |
| Шлюзы | `<<gateway>>` | единственная точка отправки во внешнюю систему | 2 |
| **Итого** | | | **26** |

В [DESIGN.md §6](../DESIGN.md) стоит оценка «~23 класса»; точная сумма по перечисленному там составу —
**26** (4 + 4 + 13 + 3 + 2). В работе реализован точный состав §6, поэтому счёт — 26.

**Почему BCE, а не «слой-в-слой» (controller/service/dao).** BCE — это модель обязанностей, а не
структура фреймворка: она отвечает на вопрос «кто с кем разговаривает» и повторяет деление лаб. 4
(экран → сервис → сущность/хранилище). При этом она не задаёт ни языка, ни фреймворка:
`<<repository>>` — это обязанность «найти и сохранить», а не таблица в базе данных.

**Как выполнено требование «без привязки к языку».**

1. Ни одного типа реализации: нет `String`, `int`, `boolean`, `UUID`, `List<…>`, `Date`/`LocalDate`.
   Вместо них — предметные типы: `Дата`, `Признак`, `ФИО`, `Гражданство`, `ИНН`, `ОГРН`,
   `НомерДокумента`, `КодРегиона`, `КодВидаДеятельности`, `Наименование`, `Адрес`, `Основание`,
   `Должность`, `ПредметРабот`, `ТрекНомер`, `ХэшСодержимого`.
2. Ни одного технического понятия: нет HTTP, REST, SQL, ORM, JSON, транзакций, потоков, исключений.
3. Структуры передачи данных (`ДанныеПатента`, `ДанныеДоговора`) — те же, что в контрактах
   [лаб. 3](../lab3-sequence-diagrams/operations.md#5-типы-параметров); перечисления
   (`СтатусПатента`, `СтатусДоговора`, `КаналУведомления`, …) — из
   [лаб. 2, раздел 5](../lab2-domain-model/README.md#5-предметные-типы-перечисления).
4. **У сущностей нет модификаторов видимости и нет методов:** только атрибуты. `-`/`+`/`#` перед
   полями не ставится (требование преподавателя), поведение целиком в управляющем слое.

## 2. Состав модели

### 2.1. Границы (4)

| Класс | Прецедент | Методы (ровно по одному на операцию) |
|---|---|---|
| `ЭкранПатента` | П01 | `зарегистрироватьПатент`, `пометитьПатентАрхивным`, `получитьСведенияОпатенте` |
| `ЭкранДоговора` | П02 | `заключитьДоговор`, `отменитьДоговор` |
| `ЭкранУведомления` | П03 | `направитьУведомлениеМВД`, `зафиксироватьВозвратУведомления` |
| `ЭкранСроков` | П04 | `пересчитатьСрокиПатента`, `настроитьНапоминания`, `зафиксироватьНарушениеСрока` |

Экран не хранит состояние формы и ничего не проверяет: он принимает данные операции и показывает
результат. Всего методов у границ — 10, по числу операций.

### 2.2. Управление (4)

| Класс | Ответственность | Операции |
|---|---|---|
| `СервисПатентов` | учёт патента, архивирование, выдача сведений; проверка ИНВ-5 | 1, 2, 3 |
| `СервисДоговоров` | заключение и отмена договора; проверки ИНВ-1, ИНВ-3, ИНВ-4 | 4, 5 |
| `СервисУведомлений` | формирование, отправка и фиксация возврата уведомления | 6, 7 |
| `СервисСроков` | единственное правило «2 месяца с даты выдачи», контрольные точки, напоминания | 8, 9, 10 |

Публичных методов у управления ровно 10, и их имена совпадают с именами операций
[DESIGN.md §3](../DESIGN.md). Приватных методов в модели нет: проверки описаны в пояснениях к
диаграммам, а не отдельными операциями, — «всё, что обещаем, должны сделать».

`СервисПатентов` при регистрации обращается к `СервисСроков` за первичным расчётом срока и созданием
контрольной точки: так правило «2 месяца» не дублируется.

### 2.3. Сущности (13)

Состав и атрибуты — ровно [DESIGN.md §5](../DESIGN.md), без `id` и без модификаторов видимости:

| Класс | Что хранит |
|---|---|
| `ИностранныйГражданин` | фио, дата рождения, гражданство, документ личности, ИНН, адрес пребывания, телефон, email, статус |
| `Патент` | серия, номер, дата выдачи, срок действия, орган выдавший, статус |
| `Регион` | код, наименование |
| `ВидДеятельности` | код, наименование, признак допустимости для патента |
| `Работодатель` | наименование, ИНН, ОГРН, адрес, тип, контактное лицо |
| `Договор` *(abstract)* | номер, вид, дата заключения, дата окончания, статус |
| `ТрудовойДоговор` | должность, режим |
| `ДоговорГПХ` | предмет, срок работ |
| `УведомлениеМВД` | дата направления, канал, номер квитанции, трек-номер, копия договора, статус |
| `КонтрольнаяТочка` | вид, плановая дата, фактическая дата, критическая, статус |
| `Напоминание` | дата отправки, канал, текст, статус |
| `Документ` | тип, имя файла, хэш, дата загрузки, источник |
| `ТерриториальныйОрганМВД` | код, наименование, адрес |

Ни у одного из 13 классов нет методов: это модель предметной области, поведение появляется в
управляющем слое.

### 2.4. Репозитории (3) и шлюзы (2)

| Класс | Слой | Методы | Обслуживает |
|---|---|---|---|
| `РепозиторийПатентов` | `<<repository>>` | `сохранить`, `найти`, `найтиДействующий` | агрегат «патент + точки + напоминания + документы» |
| `РепозиторийДоговоров` | `<<repository>>` | `сохранить`, `найтиДействующий` | договоры, поиск действующего по патенту |
| `РепозиторийУведомлений` | `<<repository>>` | `сохранить`, `найтиПоДоговору` | уведомления и доказательства отправки |
| `ШлюзЕПГУ` | `<<gateway>>` | `отправить` | канал ЕПГУ, возвращает квитанцию |
| `ШлюзПочты` | `<<gateway>>` | `отправить` | канал Почты России, возвращает трек-номер |

Репозиторий не содержит правил: он только сохраняет и находит. Шлюз только отправляет: подсистема не
отслеживает статусы доставки.

## 6. Решения и обоснования

1. **BCE сохранён.** Это единственная модель, которая одновременно отвечает на вопрос «кто с кем
   разговаривает» и не задаёт язык реализации. Переход на «controller/service/dao» дал бы те же 26
   классов с техническими именами и нарушил бы согласование с лаб. 4.
2. **Один экран на прецедент (4).** Совпадает с числом прецедентов: `ЭкранПатента` обслуживает
   операции 1–3, `ЭкранДоговора` — 4–5, `ЭкранУведомления` — 6–7, `ЭкранСроков` — 8–10.
3. **У экрана нет атрибутов.** Состояние формы — деталь реализации; в модели важно только то, что
   экран принимает данные операции и показывает результат.
4. **Правило сроков — в `СервисСроков`.** Единственное место, где живёт «2 месяца с даты выдачи».
   Правило используют операции 1 и 8–10 — иначе оно разошлось бы по четырём классам.
5. **Проверки инвариантов — в управляющем слое, не в экране.** Экран не должен быть единственной
   защитой: ИНВ-1, ИНВ-3, ИНВ-4 проверяются в `СервисДоговоров`, ИНВ-5 — в `СервисПатентов`.
6. **Репозиторий на агрегат (3).** Одно хранилище на все сущности превращается в «бог-объект»;
   три репозитория соответствуют трём агрегатам: патент (с точками и напоминаниями), договор,
   уведомление.
7. **Контрольные точки и напоминания — в агрегате патента.** Отдельного репозитория у них нет: они
   не существуют без патента (ИНВ-6) и сохраняются вместе с ним.
8. **Шлюз на канал (2), канал — параметр.** Проект уведомления формируется один раз и одинаково для
   ЕПГУ и почты; различаются только классы-шлюзы. У шлюза один метод — `отправить`.
9. **Имена — русские, как в лаб. 1–4.** Имена классов предметной области не изменены, сервисы названы
   по предметной группе, поэтому диаграммы лаб. 2–5 сопоставляются построчно.
10. **Mermaid + PlantUML + PNG для каждой диаграммы.** Mermaid читается на GitHub, PlantUML даёт
    стереотипы, кратности и PNG для вложения; обе версии содержат один и тот же состав классов.

## 7. Что убрано относительно первой версии и почему (46 → 26)

Первая версия модели проектирования строилась «на вырост» и включала темы, которых в теме 7 нет.
Состав приведён к [DESIGN.md §6](../DESIGN.md):

| Группа | Было | Стало | Почему убрано |
|---|---|---|---|
| Границы | 7 экранов, в том числе для денежных расчётов, сводных выборок и служебных действий | 4 экрана по прецедентам | у темы 7 ровно четыре прецедента; остальные экраны обслуживали чужие разделы дорожной карты |
| Управление | 10 классов, в том числе денежные расчёты, сводные выборки, разграничение доступа, журнал событий, фоновые задания | 4 сервиса | ничего из этого не следует из 7.1/7.2; фоновое расписание заменено расчётом по запросу |
| Сущности | 19 классов, в том числе денежные расчёты, учётные записи и их роли, сохранённая выборка | 13 классов §5 | эти понятия не являются предметом темы 7; учётные записи — вопрос реализации |
| Репозитории | 7 хранилищ, включая расчёты, вложения и справочники | 3 репозитория агрегатов | вложения и справочники — часть агрегатов, отдельных хранилищ не требуют |

**BCE сохранён:** пять слоёв и направление зависимостей не менялись, сокращался только состав.
Меньше классов — не «урезанная» модель, а полная модель темы: каждый из 26 классов участвует хотя бы
в одной из 10 операций, и каждая операция имеет ровно один метод-владелец.

## 8. Ограничения модели

1. **Нет кратностей на зависимостях** (`..>`): кратность показана только на ассоциациях, как в UML.
   Зависимость означает «вызывает / использует», а не «хранит ссылку».
2. **Нет диаграмм состояний и деятельности.** Жизненные циклы `Патент`, `Договор`, `УведомлениеМВД`
   видны только через перечисления статусов и смену статусов в сервисах.
3. **Нет компонентной и deployment-диаграмм.** Модель ограничена классами, как требует задание.
4. **Многопоточность и транзакционность не отражены.** Это уровень реализации (лаб. 6).
5. **Перечисления — не классы.** `СтатусПатента`, `КаналУведомления`, `ВидТочки` и другие — предметные
   типы из лаб. 2, они не входят в 26 классов.

## 10. Открытые вопросы

1. **Где создаётся контрольная точка при регистрации патента.** Сейчас — в `СервисСроков` (вызов из
   операции 1), чтобы правило срока жило в одном классе. Альтернатива — создавать точку прямо в
   `СервисПатентов`, но тогда правило дублируется.
2. **Нужен ли отдельный репозиторий справочникам.** `Регион` и `ВидДеятельности` читаются вместе с
   патентом и отдельного хранилища не получили. Если справочники начнут обновляться независимо,
   репозиторий придётся добавить.
3. **Уровень детализации проверок.** Проверки инвариантов описаны в пояснениях, а не отдельными
   методами: в лаб. 6 их состав может измениться без изменения публичных операций.
